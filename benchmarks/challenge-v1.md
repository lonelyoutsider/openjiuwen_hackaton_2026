# Challenge-v1:100 задач для диагностики харнесса

Набор авторский. Источники идей и границы переноса — docs/research-2026-11-13.md.
Это не официальный GAIA/EvalPlus/DABench и не модель распределения финального теста.
Код/вопросы/данные этих датасетов не скопированы; нет runtime-загрузок/новых зависимостей.

## Состав

| Раздел | Всего | Решаемых | Недоопределённых | Максимальный reward |
|---|---:|---:|---:|---:|
| Весь набор |100|80|20|313|
| Calibration |60|48|12|195|
| Confirmation |40|32|8|118|
| Smoke, входит в calibration |28|24|4|108|

25 задач каждого типа.40 решаемых семейств по 2 варианта, 20 отдельных сценариев
нехватки данных.60 групп: родственные варианты полностью остаются в одном разделе.
В coding варианты имеют разные дефекты, а не только новые IDs. Это не 100
независимых algorithmic families. Confirmation используется после отбора идеи;
его повторное использование для доработки лишает его роли отложенной проверки.
Разделы созданы нами; независимость от проектировщика/всей нашей процедуры не заявляется.

Reward равномерно выбирается из 1..7 независимым фиксированным RNG после
перемешивания задач, не определяется сложностью. IDs непрозрачные b000..b099.
Сид 20261113 фиксирован. Варианты, labels и reward воспроизводимы между запусками.
В task.json только task_id/task_type/instruction/reward. Expected, oracle code,
private checks, family/partition/stress доступны только offline-оценщику.
Ни один из этих признаков не передаётся планировщику/модели.

## Какие вопросы проверяем

| Тип |10 решаемых семейств |5 сценариев нехватки данных |
|---|---|---|
| Math | Взвешенное среднее; скидка+налог; целые рейсы/стоимость; периодические интервалы; кратчайший путь; вероятность без возвращения; рабочие дни; coin-change; система целых ограничений; максимальная сумма подмассива | Скорость не дана; площадь не определена периметром; неизвестно распределение; нет курса валют; неоднозначное продолжение последовательности |
| Search |3-hop документы; конъюнкция условий; смена назначения во времени; alias; отрицание; факт за 16k символов; авторитетный источник против кеша; одноимённые люди; Unicode NFC; вложенные документы | Нет места рождения; оператор не равен владельцу; устаревшая запись не определяет текущего директора; нет идентификатора человека; известен лишь год |
| Data | Signed revenue; join таблиц; dedup JSONL; quoted CSV; группировка с tie-break; сумма полного большого файла; пропуски; UTC даты; nested JSON и требуемый JSON-ответ; BOM/TSV | Нет расходов; только выборка вместо популяции; нет весов; отсутствуют цены; точное будущее не задано |
| Coding | Unicode slug; stable unique; chunks; union intervals; topo sort; run-length; decimal money в двух файлах; binary search; recursive flatten; LRU | Нет полной таблицы; proprietary checksum не задан; отсутствует политика доступа; нет timezone; не определено округление |

Все решаемые coding:существующие Python-файлы, стандартная библиотека,
unittest. Private checks включают дополнительные входы, iterable/generator,
Unicode, дубликаты, ошибки/пустые входы там, где это есть в контракте.
Референсные исправления всех 20 вариантов проходят; все 20 исходных мутантов
отвергаются оценщиком, иногда лишь private checks. Некоторые видимые тесты
специально неполны: одно их прохождение не является истинностью спецификации.
Нерешаемые coding имеют недостаточную внешнюю спецификацию; green smoke-test
не делает произвольное придуманное поведение правильным.

Числа сверяются Decimal, доли и даты — заданным форматом. JSON-ответ сравнивается
по структуре/типам, допускает 20 и 20.0, отвергает duplicate keys, bool вместо числа,
NaN, лишние ключи. Не используется LLM judge с дополнительной ценой.

## Инженерные вопросы к результатам

1. Удалось ли загрузить весь набор 100 задач без сбоев SDK и stale answer.txt?
2. Сколько reward получено при данном BUDGET, сколько осталось нерешаемых/решаемых?
3. Не приняла ли модель отсутствие факта в превью за отсутствие в полном файле?
4. Не использовала ли только первые строки большого CSV вместо полного файла?
5. Корректны ли join, dedup, знак возврата, timezone, BOM, quoted delimiter?
6. Различаются ли отсутствующее отношение и сложный, но доступный multi-hop ответ?
7. Не выдан ли coding DONE после слабого теста при неправильной реализации?
8. Сохранились ли неизменными тесты, справилась ли модель с несколькими исходниками?
9. Какие шаги повторяются без изменения файлов/результата? Сколько они стоят?
10. Были ли format/tool errors, finish_reason=length, usage_uncertain, timeouts?
11. Чем отличаются расходы/качество типов и семейств? Ошибочна ли шкала 3000/1500/1000?
12. Меняется ли преимущество кандидата при тесном BUDGET, а не только при свободном?
13. Растут ли ложные отказы или неподтверждённые ответы при экономии?
14. Совпадает ли source fingerprint реального image с выбранным runtime?
15. Работает ли plain payload, который выберется для неизвестного proxy?

## Первый запуск

Main72a942c не менять. Ветка experiment/challenge-benchmark содержит только
benchmark/оценщик/документы; runtime fingerprint прежний. Можно использовать
уже собранный its-ia:release, Docker Desktop должен работать.

```powershell
git fetch origin
git switch experiment/challenge-benchmark
py scripts/run_challenge_benchmark.py --partition calibration --format plain --budget 15000 --live
```

Один прогон, потолок 15000 учётных токенов на всё, модель qwen3.8-27b-noreason,
6 вызовов/задачу, запрошенный output cap1024 с существующей адаптацией.
Ключ скрыт, без API по умолчанию/без --live, без автоматических повторов.
Сначала preflight image fingerprint без сети; потом агент именно /app/run_agent.py
с BUDGET env. Для plain добавляется --no-json-mode: моделируется формат запроса
неизвестного proxy, но не его schema usage/HTTP-ошибки/маршрутизация.
Сеть разработки остаётся NeuralDeep; ничего из external benchmark не загружается.

Отчёт artifacts/challenge-*/benchmark.json, метаданные run.json. Отчёт включает
source commit/image/fingerprint/профиль/usage/результаты по типам и ограниченные
traces. Не коммитить сырые traces/ключи. Передать benchmark.json для анализа.
При неизвестном списании/ошибке не запускать повтор самостоятельно.

Дополнительные режимы не являются автоматическим планом расхода:
--partition smoke (28), calibration (60), confirmation (40), all (100);
--format plain/auto/json; --budget положительное число.
Сначала выполнить только приведённую команду, confirmation оставить для отбора.

## Порядок улучшений

1. Baseline на calibration60/plain. Выявить воспроизводимый класс сбоев.
2. Один opt-in механизм в отдельной ветке, unit/SDK проверки до API.
3. Сравнить baseline/candidate на одинаковом наборе и бюджете. Для расписания
   выбрать бюджет, который действительно ограничивает решение, например 5000
   на calibration; конкретную пару зафиксировать после первого отчёта.
4. Проверить выигравший механизм на confirmation40 и прежних регрессиях.
5. При росте reward без регрессий и соблюдении контракта перенести в main
   до 13 ноября 23:59 МСК. При отсутствии выигрыша сохранить 72a942c.

Не сравнивать expense/calls без solved reward. Не объявлять двадцать пропусков
верными отказами, если они вызваны budget_stop/unsupported. Отдельная метрика
missing_data_explicit_abstentions различает это. Из-за связанных вариантов
нельзя считать 100 задач 100 независимыми статистическими наблюдениями.
