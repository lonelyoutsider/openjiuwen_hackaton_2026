# Продолжение исследования: от рабочего кандидата к конкурентному харнессу

13 ноября 2026. Запрос пользователя: продолжать улучшение до дедлайна,
расширить проверку и использовать исследования/открытые решения. Это заменяет
прежнюю рекомендацию прекратить работу после 51/51. Main72a942c сохраняется
проверенной резервной версией; слово «финальная» ранее было преждевременным.

## Что 51/51 доказывает и чего не доказывает

Подтверждены сборка/image1.36GB, SDK, read-only контракт, выбранная модель,
19 конкретных правильных решений и 2 явных правильных отказа. Не подтверждены:
полные 100 новых задач, эффективность распределения дефицитного бюджета,
устойчивость к длинным данным, сложные независимые coding-тесты,
неизвестный proxy, любые меньшие BUDGET или место среди соперников.

Набор 21 был development. Его 6 детерминированных решений не обобщаются на
произвольные формулировки; новый бесплатный 100-task прогон без LLM дал 0/80.
Это проверка границ парсеров и загрузки, а не измерение качества LLM-агента.

## Аудит нашей политики

1. Планировщик делит reward на фиксированную стоимость: coding3000,
   data1500, math/search1000. Эта шкала не была откалибрована.
   В release-прогоне средняя стоимость LLM-решаемых составила coding266.7
   (7 случаев), data222.0 (2), math181.1 (2), search252.7 (2).
   Такие маленькие группы не годятся для замены глобальных констант, но
   показывают, что штраф coding в 3 раза относительно math не подтверждён.
2. Для всех задач общий предел 6 вызовов. Нет сравнения ценности следующего
   шага с ценностью начала другой задачи. Шесть повторов чтения могут
   вытеснить несколько лёгких решений.
3. Модель не видит фактический остаток token ledger; есть только предупреждение
   о последнем вызове. Budget Tracker — дешёвая проверяемая гипотеза.
4. initial_context берёт до 8000 символов на файл и 24000 суммарно, без явной
   отметки обрезки. read показывает первые 16000 без offset. Модель может
   ошибочно принять отсутствие в превью за отсутствие данных. Python способен
   читать полный файл; нужны маркировка и адресное извлечение.
5. Повторы с неизменившимся результатом не отслеживаются. Считать их только по
   action недостаточно: повторный запуск тестов после изменения кода оправдан.
6. История содержит старые сообщения и наблюдения. Они могут увеличивать
   стоимость и мешать актуальной ошибке; masking пока не измеряли.
7. Для неcoding ответов нет универсального валидатора. Самоуверенный ответ
   получает solved внутри runtime, но может быть неверным у оценщика.
8. Поддержаны существующие .py и unittest. Другие языки, pytest, создание новых
   исходников и иной packaging не поддержаны; новый benchmark специально
   остаётся в реализуемом stdlib-контракте и не скрывает это ограничение.
9. Последний live прогон был JSON/NeuralDeep. У незнакомого final proxy наша
   автонастройка выбирает plain; этот путь требует более широкой live-проверки.

## Собственные варианты для ограниченного времени

| Очередь | Один вариант | Проверка полезности |
|---|---|---|
| 1 | Явная маркировка preview/truncation + адресное чтение/поиск, без нового LLM-вызова | Длинный search/CSV не пропускаются ошибочно; вход меньше при том же reward |
| 2 | Передавать remaining token budget/calls как короткий статус | Меньше бесполезных шагов при дефиците; не растут ложные отказы |
| 3 | State-aware остановка повторной ошибки/чтения | Экономия при сохранении решения; изменение файлов сбрасывает повтор |
| 4 | Короткий первый проход с сохранением состояния и выдачей дополнительных попыток | Больше reward при одинаковом тесном бюджете, без повторной оплаты всей истории |
| 5 | Переключение на reasoning только для выбранных трудных задач | Reward выигрывает больше, чем съедает дополнительный reasoning; отдельный эксперимент |

Для планировщика целевой индекс можно записать как
reward_i * P(успех следующего этапа | наблюдения) / E(добавочные токены | наблюдения).
Это наша постановка кандидата, не уже обученная модель. Условные вероятности
не известны. Начать можно с прозрачных эвристик и фактического usage прошлых
шагов, без внешних сервисов и без использования expected/ID/будущих результатов.
Возврат к задаче должен продолжать состояние; restart с нуля удорожает два прохода.

Каждый механизм сначала отдельный. Нельзя одновременно сменить модель,
контекст, расписание и cap, а весь эффект назвать улучшением планировщика.

## Подготовленная проверка

scripts/challenge_set.py:100 authored задач, 25 каждого типа, 80 решаемых и 20
с недостающими данными.40 семейств решаемых по 2 варианта плюс 20 missing-data
сценариев. Это 60 групп, не 100 независимых шаблонов. Разделение по семействам:
calibration60 (48 решаемых, 195 reward) и confirmation40 (32, 118).
Группы не пересекаются. Smoke28 — поднабор calibration, не новый holdout.
Подробный протокол и список вопросов: benchmarks/challenge-v1.md.

Первый оплачиваемый шаг — baseline именно существующего image, plain,
calibration60, BUDGET15000. Confirmation пока не запускать. После отчёта
выбрать один механизм по реальным сбоям; сравнить при одинаковом бюджете,
а планировщик дополнительно при тесном BUDGET. Затем проверить выбранный
вариант на отложенных 40 и обязательных публичных регрессиях/контракте.

Новая серия не запускается автоматически. На каждый запуск задан потолок,
ключ остаётся локальным. Live-результатов challenge-v1 пока нет.
Main72a942c остаётся рабочей страховочной версией, не доказанным оптимумом.
До 23:59 МСК переносить только проверенное улучшение; само приближение
дедлайна не доказывает, что менять код полезно или что развитие нужно остановить сейчас.
