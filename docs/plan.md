Это план команды, а не дополнительные требования организаторов.

## Приоритет13 ноября: завершение

JSON-mode probe прошёл:12.7 учётного токена. Следует одна смешанная
A/B-пара validation-v1 (до8000 на пару), затем выбор релизного профиля,
проверка стандартной команды жюри и перенос проверенного кода в main.
Новые архитектурные эксперименты отложены.
Актуальная сверка требований и блокеры: [final-day.md](final-day.md).
Особенно срочно: madrugado=none по API GitHub и неизвестный час дедлайна.

Далее сохранён исходный план и история выбора; они не означают, что все
перечисленные механизмы должны быть реализованы до сегодняшней сдачи.

## Цель

Максимизировать reward правильных решений 100 задач при общем бюджете
output + input/10 и часовом лимите. При равном reward выбирать меньший расход.
Сохраняем настоящий openJiuwen и работающий baseline.

## Принятые решения

1. Заимствовать небольшие механизмы из Pi/Aider/OpenClaw/OpenCode/Hermes,
   не заменять весь runtime сторонним агентом. Исследование и первичные ссылки:
   [harness-research-2026-11-12.md](harness-research-2026-11-12.md).
2. Первый эксперимент — точечная замена текста в coding-файлах.
   Она должна быть отключена по умолчанию до оценки на реальной Qwen.
3. Второй эксперимент — обнаружение повторных действий без прогресса,
   с учётом аргументов, результата и изменения файлов.
4. Третий эксперимент — короткий первый проход и распределение дополнительных
   попыток по оставшимся задачам. Сначала модель фиксирована; переключение
   noreason/reasoning проверяется отдельным изменением.
5. Адресное чтение, краткие наблюдения и проверка неcoding-ответов — следующие
   кандидаты по результатам свежих трасс. LLM-суммаризация не приоритет
   для текущих коротких траекторий.

## Порядок эксперимента

- Зафиксировать исходный коммит, конфигурацию, набор и общий лимит расхода.
- Сначала проверить границы инструмента и интеграцию без платного API.
- Сравнивать baseline и один вариант на одинаковых чистых копиях задач.
- Официальные примеры не менять; validation-v1 уже использован при разработке.
- Новые coding-кейсы должны иметь независимые offline-проверки; эти проверки
  и expected не передаются агенту. Родственные варианты относятся к одной группе.
- Основные показатели: reward, weighted tokens всех попыток, время,
  ошибки формата, ложные отказы, успешность независимых проверок.
- Различать mock, Python, реальный SDK, Docker и live Qwen.
- Единичный удачный прогон не доказывает устойчивость. Спорные результаты
  повторять в рамках отдельного заранее определённого лимита.
- После отбора изменения прогнать весь диагностический набор и контракт Docker.

## Первый ограниченный live-эксперимент

A/B сравнение наличия edit-инструмента: одна и та же qwen3.8-27b-noreason,
максимум 4 вызова на задачу и 1024 выходных токена на вызов.
Предлагаемый суммарный потолок одной пары — 6000 учётных токенов
(по 3000 на вариант), без автоматических повторов пары.
Это верхняя граница, а не целевой расход. Реальный запуск выполняется
локально после подготовки кода и тестов. Первая пара завершена: reward4/9
у обоих вариантов; 1911.6/1705.3 токена, но edit не исполнился из-за
ошибок формата. См. docs/experiments/e01-result.md.

Ближайший шаг — E01b: отдельно проверить strict/recovery разбора ответа,
с edit в обоих вариантах. Лимиты остаются по 3000 на вариант / 6000 на пару;
резерв и output cap не менять одновременно. См. docs/experiments/action-format.md.
E01b завершён: strict3/9, recover5/9 при1595.8/1617.6 токена.
Механизм восстановления подтвердился на intervals; результат одного прогона.

Ближайший шаг — один небольшой JSON-mode probe через scripts/smoke_api.py
--json-mode. Совместимость Qwen/финального прокси не предполагать из документации.
После успешного probe — сравнение text/json на смешанном validation-v1,
по4000 на вариант /8000 суммарно. Протокол: docs/experiments/json-mode.md.
Резерв/call cap отдельно не менять, сырые отчёты не коммитить.

## Совместная работа

- Этот чат: постановка гипотез, разработка, ревью, анализ отчётов.
- GitHub: общая версия кода, ветки, PR, решения и результаты.
- VS Code + локальный Codex: доступ к ноутбуку, Docker и локальному API-ключу.
- Пользователь и Миша обсуждают выводы и выбирают направления; написание
  кода и подготовку проверок можно поручать Codex.
- У каждого изменения один активный исполнитель. Перед работой fetch/status;
  не редактировать параллельно те же файлы в одном checkout.
- Основная ветка содержит выбранную версию; эксперименты ведутся в отдельных
  ветках с явными флагами. Реальное улучшение не объявлять до измерений.
- Контекст переносится через AGENTS.md, docs/codex-handoff.md, plan.md
  и progress.md. Не рассчитывать на общую память чатов и IDE.
- После каждого измерения добавить конфигурацию, результат и следующий шаг
  в docs/progress.md; непроверенные сырые отчёты держать в artifacts/.
