# Исследование агентных харнессов для OpenJiuwen Challenge 2026

Дата проверки: 12 ноября 2026. Адресат: команда Its IA. Это обзор источников и проект экспериментальной программы; перечисленные изменения ещё не реализованы и не проверены на конкурсных моделях.

**Основное предложение: сохранить работающий openJiuwen-харнесс и заимствовать небольшие проверяемые механизмы. Наиболее полезные источники сейчас — mini-SWE-agent/SWE-agent, Pi, Aider, OpenCode, OpenClaw и документация Hermes. Большой персональный агент целиком не решает нашу задачу распределения ограниченного бюджета между 100 заданиями.**

## 1. Что именно оптимизируем

Условия взяты из текущих `docs/requirements.md` и `docs/progress.md` нашего репозитория. Проверенный HEAD: `b454d27bc4456bab903a7a0a52f23b533e2db3e0`. По сравнению с предыдущим изученным коммитом изменён только README; поведение харнесса не менялось.

- Все 100 заданий видны заранее. Типы: math, search, data_analysis, coding. Reward известен, но не отражает сложность.
- Основная цель — сумма reward правильных решений. Меньший расход токенов решает при равенстве баллов.
- Общая конкурсная стоимость: `C = output_tokens + input_tokens / 10`. Reasoning входит в output. Вызовы для планирования также стоят токены; скидка за кеширование не учитывается.
- Ориентир общего BUDGET — 100 000; фактический остаток прокси не сообщает.
- Нужен настоящий openJiuwen. В нашем решении закреплена версия 0.1.19.
- Runtime: час, 16 ГБ RAM, 8 логических CPU, без GPU; сеть только к API конкурсных моделей. Корневая ФС read-only, /tmp ограничен, каталог задач доступен на запись.
- Выбор из четырёх конкурсных Qwen; право переключать модели указано в регламенте. Фактическую поддержку параметров API и учёт reasoning проверяем отдельно.
- Search означает поиск по предоставленным данным, а не разрешение ходить в интернет.
- Отсутствие данных, ошибка инструмента и исчерпание лимита шагов — разные состояния. Пропуск не приносит баллов; ошибочный ответ тоже.

Контекстное окно модели и общий конкурсный бюджет — разные ограничения. Компакция может помочь поместить запрос в окно, но сама по себе не гарантирует экономию общего бюджета.

## 4. Механизмы, которые стоит перенести в нашу постановку

**А. Точечные правки вместо полного файла — первый кандидат.** Сейчас write требует полный исправленный .py, при стандартном max_output_tokens=1024. Это повышает расход и риск оборванного JSON на более длинных исходниках. Концепт Pi/Aider: path + old_text + new_text; исходный блок должен встретиться ровно один раз. Применение атомарное, после проверки пути, защиты тестов и синтаксиса; далее запускаются текущие тесты. Ошибка совпадения возвращает короткую причину и возможность перечитать конкретный фрагмент. Это не должно разрешать правки тестов, выход из workspace или обход существующих ограничений.

Экономика: сокращение выхода на 500 токенов экономит 500 конкурсных единиц; сокращение входа на 500 токенов — только 50. Это условная иллюстрация формулы, не измеренный эффект инструмента.

**Б. Более подходящие операции чтения.** Сейчас initial_context включает до 24 тыс. символов содержимого файлов; read читает только начало до 16 тыс. символов, без диапазона. Если нужная функция дальше, повторный read её не покажет. Нужны read с диапазоном строк и локальный поиск с ограничением числа совпадений. Для CSV полезны схема, типы/примеры колонок и число строк; сами вычисления выполняются Python по полному файлу. Для JSON/KB — адресные выборки. Для небольших workspace сохранить возможность дать всё сразу: лишний инструментальный раунд тоже стоит токены.

Основание: адресная загрузка из Aider/OpenCode и принципы разработки инструментов Anthropic. Это функциональное расширение, а не просто уменьшение размера промпта.

**В. Короткое наблюдение и полный результат отдельно.** OpenCode сохраняет большой результат в файл и возвращает ограниченный фрагмент. Наш вариант: краткий stdout/ошибка/код возврата/число тестов/путь к артефакту, возможность запросить нужный диапазон. Для traceback часто важен хвост, для таблицы — схема и агрегат, для поиска — совпадения с окружением. Не обрезать всё одинаково по первым N символам. Артефакты ограничивать по размеру и хранить внутри разрешённой области; путь должен реально читаться инструментом. Сам факт записи на диск не расходует LLM-токены, расход появляется при передаче содержимого модели.

**Г. Контроль повторов с учётом состояния.** Заимствовать идею OpenClaw: нормализованное действие + аргументы + отпечаток результата. Одинаковое чтение неизменившегося файла или одинаковая ошибка несколько раз — повод остановить повтор и дать один короткий recovery hint. Изменённый файл, новый результат тестов или другой фрагмент чтения должны сбрасывать соответствующий счётчик. Простое совпадение имени инструмента не означает цикл. Порог нужно подбирать под наши 4–6 шагов, а не копировать значения для длинных сессий. Лимит шагов остаётся страховкой.

**Д. Ошибки формата и обрезанный ответ.** Сейчас клиент возвращает content, не передавая finish_reason, а агент пытается разобрать JSON. При length неправильный JSON может означать слишком большую правку, а не непонимание схемы. Сначала сохранять reason и usage в диагностике, затем оценить ограниченное восстановление: меньшая правка или смена формата. Не включать бесконечный repair-loop. Точечные правки могут уменьшить саму причину.

**Е. Проверка перед принятием.** У coding уже есть автоматические тесты и защита тестовых файлов. Для остальных типов модельный answer принимается сразу. Идеи SWE-agent/Deep Agents: для арифметики — воспроизводимый расчёт; для анализа данных — явный агрегат, правило ничьей и формат; для поиска — идентификатор найденного факта/локальный источник. Проверка должна соответствовать классу задачи. Универсальный LLM-критик будет платным и не гарантирует независимости. Не добавлять его ко всем задачам автоматически. Прохождение известных coding-тестов также не доказывает прохождения скрытых.

**Ж. Два уровня бюджетирования.** У нас есть общий ledger, но очередь использует reward / фиксированная_стоимость_типа, а всем задачам задан одинаковый лимит вызовов. Предлагаемая эвристика первой попытки: reward × оценка P(correct) / оценка C. Для продолжения уже начатой задачи: reward × ожидаемый прирост P(correct) / стоимость следующего шага. Это ориентир ранжирования, не доказанный оптимум. Задачи неделимы, оценки ненадёжны, есть часовой лимит.

Для начала использовать наблюдаемые признаки: объём и тип файлов, число исходников, наличие тестов, успешность расчёта, предыдущие ошибки, необходимость перегенерации, остаток бюджета. Не выдавать самооценку уверенности модели за калиброванную вероятность. На десяти диагностических задачах нельзя надёжно обучить универсальный прогноз качества/стоимости. Не использовать expected, ID задачи или будущие шаги как признаки.

**З. Умеренная эскалация между моделями.** Возможный каскад: простая попытка noreason, затем reasoning только при полезном сигнале и достаточном резерве. Thinking может уменьшить число инструментальных ходов, но reasoning стоит как output. Нельзя утверждать, что noreason всегда выгоднее, либо что думающая модель обязательно лучше. Сравнивать суммарную конкурсную стоимость на задачу, включая неудачные попытки. Сохранять уже проверенный хороший результат при повторной попытке; новый ответ не должен автоматически затирать его.

**И. Управление контекстом — после измерения.** Полный журнал нужен для диагностики, но в каждый запрос можно посылать только полезную проекцию: условие, ограничения, краткое состояние, последние результаты и ссылки на артефакты. Для первых экспериментов простое скрытие старого объёмного stdout дешевле дополнительного LLM-саммари. При 2–4 вызовах компакция может вообще не окупиться. Нельзя удалять единственное подтверждение ответа, текущую ошибку или факт недостающих данных. При настоящем tool-calling сохранять пары вызов/результат.

**К. Учёт реального расхода и сбои.** Hermes использует реальные usage как опору для оценки текущего контекста; Ouroboros разделяет подтверждённые и неопределённые расходы. Для нас важно сохранять резервацию до получения usage и не приравнивать неизвестный расход к нулю. Сейчас любая ошибка API отключает все последующие LLM-вызовы. Это сознательный консервативный baseline, но потенциальная потеря reward при временном сбое. Перспективное улучшение — классификация ошибок: окончательный auth/budget error, подтверждённый rate limit, timeout с неизвестным выполнением. До уточнения контракта прокси автоматический повтор timeout нельзя считать бесплатным. Проверить эту логику сначала на fake API.

## 5. Статьи и руководства: что они доказывают

**The Complexity Trap, JetBrains Research, 2025.** [Статья](https://arxiv.org/html/2508.21433v3), [код](https://github.com/JetBrains-Research/the-complexity-trap). Сравнивает маскирование наблюдений и LLM-суммаризацию на SWE-bench Verified в нескольких модельных конфигурациях. Результат неодинаков: для Qwen3-32B noreason стоимость raw/masking/summary — $1.12/$0.55/$0.50, solve rate — 17/15/16%; для thinking экономия маскирования лишь около 10%. Настройки начинают маскировать после 10 наблюдений, суммаризировать после 31 хода. Наши траектории короче, цены другие. Следствие для нас — сначала измерить объём наблюдений, затем пробовать дешёвое маскирование; обещать двукратную экономию нельзя.

**SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering, 2024.** [Статья](https://arxiv.org/abs/2405.15793). Обосновывает важность интерфейса между моделью и средой: навигации, редактирования, наблюдений, запуска проверок. Для нас это аргумент исследовать инструменты и сообщения об ошибках как самостоятельные компоненты. Ранние benchmark-цифры не являются прогнозом качества конкурсных Qwen.

**Executable Code Actions Elicit Better LLM Agents / CodeAct, 2024.** [Статья](https://arxiv.org/abs/2402.01030). Рассматривает исполняемый Python как объединённое пространство действий. Наш python-инструмент уже реализует часть идеи: чтение, фильтрацию и расчёт можно сделать одной программой вместо серии разговорных шагов. Не следует печатать весь dataset или добавлять неограниченную оболочку ради буквального копирования архитектуры.

**BORA-BUDGET: Learning When to Think Under a Token Budget, EMNLP 2026.** [Статья и PDF](https://aclanthology.org/2026.emnlp-main.408/). Рассматривает распределение платного thinking после дешёвого начального ответа, полезность и риск замены ответа. Для нас близка идея оплачивать эскалацию там, где ожидается прирост качества, и сохранять удачный результат. Авторы сами отмечают неоднородный перенос на другие типы задач; готовый контроллер не следует считать валидированным на нашем наборе.

**Anthropic: Writing effective tools for agents; Effective context engineering for AI agents.** [Инструменты](https://www.anthropic.com/research/writing-tools-for-agents), [контекст](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents). Практические принципы: ясные описания и границы инструментов, содержательные экономные ответы, адресная загрузка контекста и оценивание на реальных задачах. Это инженерные рекомендации, а не гарантия определённого процента улучшения.

**LangChain: Improving Deep Agents with harness engineering, 2026.** [Разбор](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering). Авторы сообщают рост Terminal Bench 2.0 с 52.8 до 66.5 на фиксированной GPT-5.2-Codex при изменениях харнесса. Полезен метод: смотреть трассы, искать конкретные ошибки, изменять ограниченное число компонентов, проверять результат. У нас другая модель и цель по бюджету; эта цифра не переносится.

**LangChain: How We Benchmark Deep Agents.** [Разбор](https://www.langchain.com/blog/how-we-benchmark-deep-agents). Полезны небольшой фиксированный набор для итераций, более полный end-to-end набор и отдельные тесты компонентов. В статье подчёркивается необходимость повторов из-за вариативности агентов. Это ближе к нашей текущей потребности, чем запуск большого стороннего benchmark целиком.

**Ouroboros: A Self-Developing Frontier Coding Agent with Reviewed Core Evolution, 2026.** [Технический отчёт](https://arxiv.org/abs/2608.08311). Интересно разделение живого развития и замороженных снимков для оценки. Внешние результаты заявлены авторами для других моделей и сред; они не доказывают полезность самоизменения во время часового конкурсного запуска. Практический перенос — улучшать наш код по трассам между экспериментами, фиксировать версию и проверять её.

## 6. Где находимся мы

Источник измерений — журнал команды и переданные пользователем отчёты, а не новый запуск в ходе исследования.

| Проверка | Измеренный результат |
|---|---|
| 8 официальных примеров, только детерминированная часть | 6/8, reward 16/20, ноль LLM-токенов |
| 8 официальных примеров, реальная Qwen + fallback | 8/8, reward 20/20, 4 вызова, 850.6 учётного токена |
| Авторский validation-v1, первый live-прогон | 7/8 решаемых, reward 18/21; 24 вызова, 2169.9 токена |
| Повтор только двух проблемных задач после изменения инструкции | Одна решена, по второй корректно обнаружена нехватка данных; 3 вызова, 297.9 токена |

Последняя строка не является новым полным score. Полный validation после изменения инструкции не прогонялся. Официальные примеры и validation-v1 уже использовались при разработке; для отбора новых идей нужен свежий набор. На v1 две coding-задачи проходили дополнительные offline-проверки, но это не доказательство обобщения на весь скрытый coding.

Что уже реализовано: настоящий openJiuwen, детерминированный первый проход, локальные инструменты, приватная копия workspace, защита тестов, автоматический unittest, общий бюджет с предварительной резервацией, ограничение шагов/времени, opt-in диагностика. Полноценного обученного оценщика стоимости, проверки всех неcoding-ответов, адресного read, patch и обнаружения циклов пока нет.

## 7. Рекомендуемая программа экспериментов

**До изменений:** сохранить baseline-коммит и конфигурацию; использовать свежие задачи с независимой проверкой, сначала весь набор прогнать baseline. Для быстрого исследования достаточно начать с 16–24 новых задач, но такой объём всё ещё не репрезентативен. Включить все 4 типа, длинный файл, несколько файлов, неоднозначные данные, недостающие данные и ошибки инструментов. Родственные варианты держать одной группой. Сравнивать отдельные изменения, затем только выигравшую комбинацию.

| Порядок | Одна экспериментальная переменная | Что проверяет | Когда принимать |
|---|---|---|---|
| 1 | Добавить точечную замену к текущим coding-инструментам | Снижаются ли выход, повреждения JSON и стоимость длинных исправлений | Не хуже независимые coding-проверки; ниже расход или выше reward при том же лимите |
| 2 | Добавить state-aware обнаружение повторных действий | Сокращаются ли бесполезные шаги без раннего прекращения решаемых задач | Уменьшение повторов/расхода при сохранении reward; нет роста ложных остановок |
| 3 | Заменить фиксированное распределение шагов на два прохода с ограниченной эскалацией | Помогает ли отложить трудную задачу, сначала решить другие и вернуться с резервом | Больше суммарный reward при одинаковом общем бюджете и времени |

Адресное чтение, формат наблюдений и проверку ответов выделить в следующие отдельные варианты, если свежие трассы покажут соответствующие ошибки. Observation masking проверять на длинных/многословных траекториях; не делать его обязательным для всех.

В третьем эксперименте сначала менять только распределение вызовов, сохраняя модель. Переключение noreason/reasoning — отдельная следующая переменная: иначе нельзя понять источник эффекта. Возврат к задаче должен продолжать сохранённое состояние, а не оплачивать полное исследование заново.

**Измерения:** reward, число правильных решений по типам, input/output/reasoning и конкурсная сумма, вызовы, время, коды завершения, ошибки JSON и length, повторные действия, явные отказы при наличии данных, ответы без данных, результаты независимых coding-проверок. Показывать максимум награды на каждом наборе и расход неуспешных попыток. Сравнение политики распределения проводить при реально ограничивающем бюджете: если все задачи дешёво решаются и бюджет не заканчивается, преимущество планировщика не видно.

**Правило отбора:** reward имеет приоритет; при одинаковом reward выбирать меньшую конкурсную стоимость. Дополнительно сравнивать кривую reward от бюджета и время. Не заменять цель только отношением reward/tokens. Temperature=0 не гарантирует одинаковый результат; повторять спорные сравнения в рамках заранее заданного расхода.

Живые API-прогоны в рамках этого исследования не выполнялись. Перед следующей серией нужно зафиксировать её общий лимит, количество вариантов и повторов. Mock-тесты резервирования, путей, атомарности правок и циклов выполнить до расходования API. Проверки настоящего openJiuwen и Docker по конкурсному контракту остаются обязательными после отбора изменений.

## 8. Что пока не включать в конкурсную ветку

- Полную замену openJiuwen на другой агентный фреймворк.
- Постоянную память персонального ассистента, социальные каналы, heartbeat и самоизменение runtime.
- Swarm с несколькими планировщиками без измеренного преимущества: каждый участник оплачивает собственные промпты и ответы.
- Интернет-поиск, внешние MCP-сервисы, платные сторонние API и runtime-скачивание инструментов.
- LLM-саммари или LLM-критика на каждом коротком задании.
- Автоматические повторные API-запросы с неизвестным списанием.
- Экономию от prompt caching как часть конкурсной формулы.
- Подгонку под task IDs, expected, формулировки восьми примеров или текущие ответы validation.

Это приоритеты для текущего срока и контракта, а не утверждение, что перечисленные механизмы бесполезны вообще.
