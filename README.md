# openJiuwen Challenge 2026 — Its IA

Команда: Иван и Миша. Рабочий репозиторий соревнования 7–13 ноября 2026.

## Что решаем

Харнесс получает 100 задач и общий бюджет. Цель — максимальная сумма reward
за правильные ответы. Цена LLM-вызовов: output + input/10, включая reasoning
в выходе, без скидки за кеш. Прогноз расхода нужен для выбора задач и стратегии.

Подтверждённые правила и вопросы: [docs/requirements.md](docs/requirements.md).
План: [docs/plan.md](docs/plan.md). Измерения: [docs/progress.md](docs/progress.md).

## Текущий результат

Первый baseline исполняется через Workflow и Runner openJiuwen 0.1.19.
Поддерживает узкие семейства из официальных примеров: арифметика склада,
суммирование отфильтрованных строк CSV, поиск даты рождения и города
работодателя в локальной KB. Числа и ответы вычисляются из текущих данных.
Для остальных задач добавлен ограниченный LLM-решатель через тот же workflow.
Он читает файлы, вычисляет Python-кодом, исправляет существующие Python-исходники
и запускает unittest. Детерминированная фаза всегда выполняется первой.

Реальная Qwen с новым решателем ещё не проверена. Проверки с имитацией API
подтверждают интеграцию, а не качество модели или результат скрытого теста.

На 8 публичных примерах: **6 правильных ответов, 16/20 баллов, 0 LLM-вызовов**.
Это проверка на примерах, а не оценка скрытого теста или готовность к отбору.
Перед запуском оценщик удаляет expected из копии task.json. Решатель получает
только разрешённые поля. expected читает исключительно локальный оценщик.

## Windows: первый API-вызов без установки библиотек

Python 3.14 годится для отдельного диагностического скрипта, но выбранный
openJiuwen требует Python >=3.11,<3.14. Основной агент запускаем в Docker/Python 3.12.

```powershell
git clone https://github.com/lonelyoutsider/openjiuwen_hackaton_2026.git
cd openjiuwen_hackaton_2026
py scripts/smoke_api.py
```

Вставить ключ из кабинета в скрытый запрос. Ключ не сохраняется в файл и
не передаётся как аргумент командной строки. Если LLM_API_KEY задан, берётся
из окружения. Скрипт делает ровно один chat/completions запрос, max_tokens=32,
модель qwen3.8-27b-noreason, без автоматических повторов, выводит ответ и usage.
Это диагностика API, не конкурсный агент. Проверено с mock HTTP; реального
запроса с ключом команды ещё не было. Python 3.14 здесь отдельно не запускался.

Docker Desktop: https://docs.docker.com/desktop/setup/install/windows-install/
Выбрать WSL 2 backend, затем открыть Docker Desktop и новый PowerShell:
`docker version`, `docker run --rm hello-world`, `wsl -l -v`.

## Быстрый старт: Python 3.12

```bash
python -m venv .venv
# Linux / WSL:
source .venv/bin/activate
# Windows PowerShell вместо предыдущей строки:
# .venv\Scripts\Activate.ps1
python -m pip install -r requirements.lock
python -m unittest discover -s tests -v
python scripts/evaluate_examples.py
```

Оценщик создаёт временную копию задач и не меняет originals. Все 8 примеров
доступны в examples/task-dir. Для проверки парсеров без установки openJiuwen:
`python scripts/evaluate_examples.py --engine stdlib`.
Это диагностический режим, для соревнования используется режим openjiuwen.

Запуск на новом каталоге задач:

```bash
python run_agent.py --tasks-dir /path/to/tasks
```

Повторный запуск на каталоге с answer.txt отклоняется, чтобы старые ответы
не влияли на оценку. Для нового эксперимента использовать чистую копию задач.
Ответ сохраняется атомарно рядом с task.json сразу после решения; рабочие
файлы читаются из workspace/. Дополнительный its_ia_result.json содержит
статус и расход, а не секреты или полный диалог. Пропущенным задачам
answer.txt не создаётся. Детерминированная фаза не исполняет код из задач.
В LLM-режиме Python-код и тесты запускаются отдельным ограниченным процессом
на временной копии workspace; ограничения описаны ниже.

## Первый ограниченный эксперимент с LLM

После обновления репозитория, в PowerShell:

```powershell
git pull --ff-only
docker build --progress=plain -t its-ia:agent .
py scripts/run_live_examples.py
```

Вставить ключ из кабинета в скрытый запрос. Ключ передаётся Docker через
окружение, не сохраняется и не появляется в аргументах командной строки.
Скрипт запускает 8 публичных примеров с бюджетом **3000 учётных токенов**,
лимитом 4 вызова на нерешённую задачу и 1024 выходных токена на вызов.
Шесть поддержанных примеров решаются без LLM, две coding-задачи идут в fallback.
Число правильных ответов новой версии узнаём только после реального запуска.
Не повторять эксперимент автоматически при ошибке: сначала разобрать лог.

`LLM_MODEL` выбирает одну из четырёх разрешённых моделей; по умолчанию
qwen3.8-27b-noreason. Переключение по типу задач пока не реализовано.
Конкурсный CLI автоматически включает LLM при наличии LLM_API_KEY;
`--no-llm` отключает. Оценщик примеров включает LLM только с явным `--llm`.

## Docker

```bash
docker build -t its-ia:baseline .
docker run --rm --read-only --tmpfs /tmp:rw,size=2g \
  --network none --cpus 8 --memory 16g --pids-limit 512 \
  --cap-drop ALL --security-opt no-new-privileges \
  -e HOME=/tmp -e BUDGET=100000 \
  -v /absolute/path/to/clean-tasks:/data/tasks:rw \
  its-ia:baseline --tasks-dir /data/tasks
```

Сеть текущему baseline не нужна. При подключении LLM использовать сеть прокси
организаторов и передавать LLM_BASE_URL, LLM_API_KEY. Ключ проверяющих не будет
совпадать с ключом команды. Ничего не скачивать при запуске.

Пользователь подтвердил сборку baseline на Docker Desktop/WSL2: примерно
3 минуты, образ DISK USAGE **1.36GB**, CONTENT SIZE 298MB. Запуск с read-only
root и без сети дал 6/8 и 16/20. Это проверка версии до LLM-расширения;
новую версию нужно собрать повторно. Новых зависимостей расширение не добавляет. Зафиксированные версии зависимостей
получены из отдельного проверенного окружения; перенос на Windows отдельно
не проверялся. Образ надо проверить в Docker Desktop/WSL2 до сдачи.

## Планировщик, расход и невыполнимость

Сначала выполняются все поддержанные детерминированные решения. Оставшиеся
задачи сортируются по reward/эвристической стоимости (coding 3000,
data_analysis 1500, math/search 1000). Это начальная политика, не обученный
оценщик и не измеренная вероятность успеха.

LLM-клиент последовательный, интервал не менее 1.05 секунды. Перед вызовом
резервируется число UTF-8 байтов JSON + 1024 единицы входа + max_output*10;
после ответа резерв заменяется usage: prompt + 10*completion в десятых долях
учётного токена. Это консервативная эвристика токенизации, не формальная гарантия
для любого токенизатора. Reasoning из completion_tokens_details уже включён
в completion_tokens проверенного формата и второй раз не добавляется.
Кеш не даёт скидки. При ошибке/неизвестном usage резерв остаётся списанным,
дальнейшие LLM-запросы останавливаются. Автоповторов нет.

Для coding изменения делаются во временной копии. После положительного
результата unittest и проверки сохранности тестов переносятся только изменённые
существующие .py-исходники; ответ DONE сохраняет харнесс. Ноль обнаруженных
тестов не считается успехом. Неуспешные правки в оригинал не переносятся.
Поддержка новых файлов и иных тестовых фреймворков пока отсутствует.
Прохождение публичных тестов не гарантирует скрытых тестов.

Python-инструмент имеет таймаут и лимиты CPU/RAM/вывода в Linux; окружение
очищено от API-ключа. Audit guard блокирует сеть, запуск подпроцессов, чтение
вне workspace/stdlib и запись тестов. Это защита от случайных действий,
**не полноценная песочница для враждебного кода**. Изоляцию обеспечивает
ограниченный контейнер проверяющих. Никакого доступа к expected инструменту нет.

Статус solved означает наличие принятого харнессом ответа; для обычных LLM-ответов
это не независимое подтверждение правильности. insufficient_data может быть
ошибочным отказом модели; unsupported — ограничение решателя, не доказанная
невыполнимость. Дообученного оценщика и собранных реальных траекторий пока нет.
